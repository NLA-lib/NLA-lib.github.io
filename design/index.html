How NLA-lib defines things

AlgorithmsTheoryReferencesLean reference

NLA-lib aims to serve as a foundation for the formalization of new and existing numerical linear algebra results.

Some results in NLA are foundational and straightforward to state formally, but do not appear in existing libraries such as Mathlib. This includes things like the Weyl’s inequalities, Cauchy interlacing, the Eckart–Young theorem, the Moore–Penrose pseudoinverse, Jackson’s theorem, etc. For such results, the main benefit of NLA-lib is that it helps people avoid repeatedly proving the same thing for their own work, but it would be appropriate to upstream many of these results to Mathlib.

On the other hand, many things in NLA are much blurrier. The most apparent issue is that natural language results in NLA are often stated with implicit definitions, quantification, integrability assumptions, orders of limits, etc. Perhaps more significant is the fact that there are often many slightly different statements describing the same general concept (e.g. describing how Gaussian matrices give an oblivious subspace embedding). While a standardized library of formalized math can help simplify and clarify the landscape some, the nature of the field means that there are no single “canonical” statements of many results.

Algorithms

The main benefit of NLA-lib is in facilitating the formal verification of statements about algorithms. Before describing how we handle this, we provide some examples highlighting some key issues that make formalizing algorithm analysis tricky.

Mathematical quantities

Lots of the analyses of algorithms in NLA are essentially proving things about of simple mathematical objects. For example, the randomized SVD of \mathbf{A} with test matrix \mathbf{\Omega} is the matrix \mathbf{P}_{\mathbf{A}\mathbf{\Omega}}\mathbf{A}, where \mathbf{P}_{\mathbf{A}\mathbf{\Omega}} is the orthogonal projector onto the range of \mathbf{A}\mathbf{\Omega}. Likewise, the conjugate gradient method (CG) for solving \mathbf{A}\mathbf{x} = \mathbf{b} with \mathbf{A} positive definite mathematically as a certain minimizer.

Def. Let \mathbf{A}\in\mathbb{R}^{n\times n} be positive definite and \mathbf{b}, \mathbf{x}_0\in\mathbb{R}^n. Define \mathbf{x}_\star = \mathbf{A}^{-1}\mathbf{b} and \mathbf{r}_0 = \mathbf{b} - \mathbf{A}\mathbf{x}_0. The k-th CG iterate is \mathbf{x}_k := \argmin_{\mathbf{x} \in \mathbf{x}_0 + \mathcal{K}_k(\mathbf{A}, \mathbf{r}_0)} \|\mathbf{x}_\star - \mathbf{x}\|_{\mathbf{A}}, \qquad \mathcal{K}_k(\mathbf{A}, \mathbf{r}_0) := \operatorname{span}\{\mathbf{r}_0, \mathbf{A}\mathbf{r}_0, \ldots, \mathbf{A}^{k-1}\mathbf{r}_0\}.

From such definitions we can prove theorems such as classical condition number convergence bound for CG:

Theorem. The CG iterates satisfy \frac{\|\mathbf{x}_\star - \mathbf{x}_k\|_{\mathbf{A}}}{\|\mathbf{x}_\star - \mathbf{x}_0\|_{\mathbf{A}}} \le 2 \left( \frac{\sqrt{\kappa} - 1}{\sqrt{\kappa} + 1} \right)^k, where \kappa = \lambda_{\max}(\mathbf{A}) / \lambda_{\min}(\mathbf{A}) is the condition number of \mathbf{A}.

In these cases, the interesting thing is how the mathematical objects behave, not how we compute them, so it is natural to reason about the output itself.In fact, we often assume we can actually compute things like eigenvalues! Formalizing results of this type encounters the issues described above, but ultimately is relatively straightforward.

Specifying an implementation

If we want to understand stuff about a computing a quantity, then we must specify an algorithm, i.e. a sequence of steps that computes the quantity. For CG the usual choice is the recurrence of Hestenes and Stiefel:Hestenes, Magnus R., and Eduard Stiefel. 1952. “Methods of Conjugate Gradients for Solving Linear Systems.” Journal of Research of the National Bureau of Standards 49 (6): 409–36. https://doi.org/10.6028/jres.049.044..

CG(A,b,x,k):
    r = b - A x
    p = r
    for j = 1, 2, ..., k:
        α = (r, r) / (p, A p)
        x = x + α p
        r' = r - α A p
        β = (r', r') / (r, r)
        p = r' + β p
        r = r'
    return x

In exact arithmetic, one can prove that CG(A,b,x_0,k) returns the CG iterate \mathbf{x}_k, and hence enjoys any of the properties we have proved about this mathematical quantity.

Of course, the above implementation is not the only way to compute \mathbf{x}_k; other implementations, for instance those based on the Lanczos recurrence, can also be used to compute the same mathematical quantity. Moreover, the recurrence above is not even fully specified; it uses inner products, sums of vectors, and products with \mathbf{A}, but each of these can be computed in several ways. While these implementations all produce \mathbf{x}_k in exact arithmetic, their costs, and their behavior in inexact arithmetic, may differ.

In NLA, we are used to implicitly choosing the level of granularity that is relevant based on informal knowledge and vibes. For example, in the implementation of CG we may not specify how inner products are performed, because we have some kind of understanding that any reasonable implementation of inner products will produce similar results. Yet, we specify the order of vector operations because these do have a large qualitative impact on the output.

In NLA-lib we allow any base-operations, and promises about their accuracy, to be specified. For example, CG can be written at the level of vector operations, with promises about how accurately these operations are computed. Alternately, specific arithmetic routines can be used in place of generic vector operations, with promises about how accurately arithmetic is performed. In general, these choices are modular, which allows various computational kernels to be combined easily.

Measuring costs

Once an implementation is specified down to individual base operations, we can count costs. A typical result gives the cost and the accuracy together. Consider for example the following stylized example.

Def. Let a \oplus b denote floating point addition: the floating point number nearest to a + b. If no overflow or underflow occurs, then a \oplus b = (a + b)(1 + \delta) for some \lvert\delta\rvert \le u, where u is the unit roundoff.

We can then define a standard summation algorithm:

SUM(x_1, ..., x_n):
    s = x_1
    for i = 2, ..., n
        s = s ⊕ x_i
    return s

We can then prove something like the following:

Theorem. For any floating point numbers x_1, \ldots, x_n, if no overflow or underflow occurs, SUM uses n-1 floating point additions and returns a value s satisfying \Bigl\lvert s - \sum_{i=1}^n x_i \Bigr\rvert \le \bigl((1+u)^{n-1} - 1\bigr) \sum_{i=1}^n \lvert x_i \rvert.

A lot of formalization of numerical algorithms has this shape. Libraries such as Flean, FloatSpec and FloatLib formalize floating point formats and rounding in Lean, and SciLean is a library for writing numerical programs in Lean. With these, an algorithm is an ordinary Lean function, and a theorem is a statement about the value it returns.

Not so fast!!

The astute reader will recognize that the theorem above is meaningless without the definition of SUM. Consider for example the following example.

EXACT_SUM(x_1, ..., x_n):
    s = x_1
    for i = 2, ..., n
        s = s + x_i
    return fl(s) ⊕ 0

Theorem. For any floating point numbers x_1, \ldots, x_n, if no overflow or underflow occurs, EXACT_SUM uses one floating point addition and returns a value s satisfying \Bigl\lvert s - \sum_{i=1}^n x_i \Bigr\rvert \le u \sum_{i=1}^n x_i .

This theorem is true, but it asserts an error and cost that are each seemingly too good to be true. The issue is that EXACT_SUM is not something a computer can compute efficiently: it adds real numbers exactly and rounds once at the end. However, nothing in Lean prevents this, since the real numbers and their exact arithmetic are available to every definition. In particular, statements about cost must also discuss what an algorithm is not allowed to do. Yet, this is only stated implicitly in essentially all numerical analysis results.

Even more!!

This is not the only way we can produce statements that are seemingly too good to be true. For example consider the program:

OVERFLOW_SUM(x_1, ..., x_n):
    a = largest floating point number
    s = a ⊕ a         // always overflows
    return 0

Theorem. For any floating point numbers x_1, \ldots, x_n, if no overflow or underflow occurs, OVERFLOW_SUM uses one floating point addition and returns a value s satisfying \Bigl\lvert s - \sum_{i=1}^n x_i \Bigr\rvert \le u \sum_{i=1}^n x_i .

Here, the addition in OVERFLOW_SUM overflows on every input, so the hypothesis “no overflow or underflow occurs” is never satisfied and the theorem is vacuously true.

How NLA-lib handles things

Both of the examples above are easy to observe because the programs are simple and can be inspected directly. However, for more complicated algorithms, it is easy to imagine cases where very subtle issues slip through the cracks. Having to check that the implementation of an algorithm is correct by hand undermines much of the value of formal verification; in particular, it requires large levels of human trust.

In NLA-lib, we define routines as a fixed tree of operation calls and control flow. An operation model dictates which operations a routine may call (e.g. scalar +, dot, a product with \mathbf{A}, etc.), what each operation guarantees, and how much each call costs. The operations, guarantees, and costs are flexible so that users can prove results using subroutine that have not been anticipated by the library. At the same time, we provide several ``standard’’ collections of base operations (e.g. BLAS1 operations to relative accuracy, the standard model of floating point arithmetic, etc.) which specify base operations, their guarantees, and their costs.

Our approach is modular by design. For instance, one can prove results about CG assuming that vector operations are performed to relative accuracy, and then easily extend this to a result in the standard model of floating point arithmetic by linking this with existing bounds for vector operations. Likewise, users may specify an algorithm such as the randomized SVD in terms of abstract operations like “orthogonalize” and then realize a theorem about arithmetic costs by “plugging in” a particular scheme such as Gram–Schmidt QR.

Trust

We believe the main value of NLA-lib is that it allows users to outsource trust of many things to the library itself. In particular, a user who trusts that NLA-lib’s definition routines and standard collections of base operations are sound can have faith in statements about cost and accuracy proved using NLA-lib. As more users adopt NLA-lib for their own work, issues with the library are more likely to be identified, and the overall trust in the library will increase.

Our approach does not guarantee that the way a particular algorithm is defined in NLA-lib matches any natural language or software definitions. However, we again hope that centralization will increase trust in the NLA-lib provided algorithms, since users can identify and fix bugs.

Formalizing software

Our approach for formalization differs from some other related formalization projects in aim. In particular, we aim to be able to reason about the theoretical analysis of algorithms, including in models of inexact arithmetic.

One might argue that what we should care about is whether the “real-world” implementations work. For example, it would be wonderful if when you called an eigensolver in LAPACK, it would be guaranteed to succeed and produce an accurate output. However, doing so would require reasoning about FORTRAN, the compiler, whatever implementation of BLAS is being used, and the physical system the code is being run on.

An intermediate approach is to write the software in Lean itself and then reason about this software. Lean is a programming language as well as a proof assistant, and projects such as SciLean (scientific computing in Lean) and FloatLib (verified floating point arithmetic in Lean) make it possible to write numerical code that runs reasonably fast. One can then use Lean to prove stuff about the outputs of these codes.

Such algorithms can inherent much of the error bounds from NLA-lib. In particular, the way we define error bounds typically involve showing that our routines satisfy certain mathematical conditions, which then imply error bounds. A bridge showing that other software satisfies the relevant mathematical conditions allows the error bounds to be applied.
